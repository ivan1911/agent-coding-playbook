# Agent Coding Playbook

Как с помощью AI-агента довести идею бизнеса до готового кода и как устроить репозиторий, чтобы агент работал предсказуемо.

Все примеры вымышленные: мы показываем подход, а не конкретные сервисы.


## Подход в двух словах

Наивный «промпт → код» ломается тремя способами:

| # | Провал | Что лечит |
|---|---|---|
| 1 | Дрейф терминов и допущений | контекст: глоссарий, ADR |
| 2 | Код не там и не той формы | архитектура: слои, таблица «куда что класть» |
| 3 | Нет проверки | процесс: TDD, ревью после каждой задачи |

**Конвейер, а не промпт.** Agent coding — это цепочка фаз. У каждой фазы есть вход и готовый артефакт на выходе. Повторить фазу дёшево, переписать всё с нуля дорого.

**Архитектура — интерфейс агента.** Слои, глоссарий, ADR и golden reference — это контракт, по которому агент находит место для кода, а не изобретает его.

**Три уровня:**

1. **Идея.** Бизнес пишет эпик в трекере задач.
2. **Планирование.** Команда в док-хабе (репозитории с глоссариями всех сервисов) прорабатывает эпик картой (wayfinding) и режет его на тикеты «сервис × сценарий» с `Blocked by`.
3. **Реализация.** Внутри каждого сервиса: проектирование одной сессией (`grill-with-docs` → `to-spec` → `to-tickets`), затем исполнение одним из двух маршрутов.

Исполнение:

- **Маршрут 1, ручной контроль.** `implement` по каждому тикету в отдельной сессии, внутри TDD, в конце `code-review`.
- **Маршрут 2, весь spec сразу.** `writing-plans` режет PRD на мелкие шаги, `subagent-driven-development` выполняет их свежими субагентами с ревью после каждой задачи.

## Шпаргалка: фаза → скилл → артефакт

| Уровень | Фаза | Скилл | Артефакт |
|---|---|---|---|
| 1 | Эпик | — | эпик в трекере задач |
| 2 | Wayfinding | `wayfinder` | `.scratch/<effort>/map.md` + исследовательские тикеты |
| 2 | Декомпозиция | `to-tickets` | тикеты «сервис × сценарий» с `Blocked by` |
| 3 | Проектирование | `grill-with-docs` (+ `domain-modeling`) | `CONTEXT.md`, `docs/adr/*` |
| 3 | Спека | `to-spec` | `PRD.md` |
| 3 | Тикеты (только для маршрута 1) | `to-tickets` | `.scratch/<feature>/issues/NN-*.md` |
| 3 | Исполнение · маршрут 1 | `implement` | код |
| 3 | Исполнение · маршрут 2 | `writing-plans` + `subagent-driven-development` | план + код |
| 3 | Ревью после задачи | `code-review`, `verification-before-completion` | зелёные тесты, ревью |

## Документы сервиса

| Документ | Когда читает агент | Что в нём |
|---|---|---|
| `CONTEXT.md` | всегда | глоссарий: один термин на понятие + список `_Avoid_` |
| `docs/adr/` | при проектировании | решения, которые трудно откатить, удивляют без контекста и имели реальную альтернативу |
| `architecture.md` | перед написанием кода | таблица «куда что класть» + «когда ломать правило» |
| `CODING_STANDARDS.md` | при ревью | рубрика ревью |

Каждое правило живёт ровно в одном документе. Второй документ ссылается на него, а не повторяет.

Пример всех четырёх — в [`examples/`](examples/).

## С чего начать

1. **Введи глоссарий** (`CONTEXT.md`). Самый дорогой по эффекту шаг: без единого языка конвейер рассыпается на дрейфе.
2. **Раздели доки по моменту.** Гид для написания кода и чек-лист ревью.
3. **Напиши `architecture.md`.** Таблица «куда что кладётся» + секция «когда ломать правило».
4. **Пройди один реальный прогон** на небольшой фиче: grill → spec → tickets → implement → verify.
5. **Подключи субагентный конвейер** только после этого.

Сопротивление возникает на шагах 1–3: это рутина, которая «не пишет код». Но именно она делает шаги 4–5 предсказуемыми.

## Инструменты

- [opencode](https://opencode.ai/docs) — среда, в которой идёт вся работа: сессии, скиллы, MCP, права.
- [codegraph](https://github.com/colbymchenry/codegraph) — граф символов и вызовов вместо grep-циклов.
- [Matt Pocock skills](https://github.com/mattpocock/skills) — `grill-with-docs`, `to-spec`, `to-tickets`, `implement`, `wayfinder`, `code-review`, `triage`.
- [superpowers](https://github.com/obra/superpowers) — `brainstorming`, `writing-plans`, `subagent-driven-development`, `verification-before-completion`.
- [LiteLLM](https://github.com/BerriAI/litellm) — proxy и единый шлюз к моделям; [guardrails](https://docs.litellm.ai/docs/proxy/guardrails/quick_start) маскируют ПДн, токены и секреты до отправки запроса в модель.
- Локальный markdown-трекер — `.scratch/` живёт в git: историю правок видно, её можно ревьюить.

Подробности — в [полном материале](docs/agent-coding.pdf).
