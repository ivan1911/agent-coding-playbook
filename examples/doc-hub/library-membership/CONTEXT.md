# Context: library-membership

## Domain

Ведение читательских профилей сети городских библиотек: учёт читателей, их абонементов и предпочтений, предоставление краткой информации о читателе библиотекарю и внешним каналам.

## Language

### Хелпдеск

Внешняя система обращений читателей. Инициатор вызова API library-membership: когда читатель обращается в поддержку, Хелпдеск передаёт `card_number` и вызывает `GET /reader` для идентификации.

- 404 — читатель не найден → предложить оформить читательский билет на портале библиотеки
- rules_accepted=false — читатель найден, но не принял правила пользования → предложить принять правила на портале
- rules_accepted=true — читатель доступен для обслуживания, ответ содержит список активных абонементов (`subscriptions`) и `reader_id`

_Avoid_: тикетница, очередь обращений

### Мобильное приложение

Клиентский канал библиотеки. Внешний потребитель API library-membership: проверяет по `card_number`, приняты ли правила пользования, и если нет — получает текст инструкции по их принятию.

_Avoid_: приложение, мобилка

### API-шлюз

Посредник между внешними каналами (Хелпдеск, Мобильное приложение) и library-membership: проверяет OAuth2-токен и скоуп эндпоинта, затем проксирует вызов.

_Avoid_: gateway, прокси

### card_number

Номер читательского билета. Создаётся не library-membership, а выдаётся при регистрации на портале библиотеки и передаётся в систему через SSO-сервис. Внешние каналы идентифицируют читателя по нему.

Хранится в `reader.card_number` как unique-ключ для поиска. Возвращается в API как идентификатор читателя для внешних систем.

_Avoid_: ID читателя, номер карты

### reader_id

Внутренний идентификатор читателя. Автоинкрементный PK таблицы `reader`. Возвращается в API как стабильный идентификатор для последующих запросов (`personal_data`, `summary`, `preferences`). Не зависит от возможной перепривязки `card_number` ↔ `account_id`.

_Avoid_: profile_id, ID профиля

### account_id

Идентификатор учётной записи читателя в SSO-сервисе. Связь `account_id` → `card_number`: 1:1, может измениться при объединении учётных записей. Используется для интеграции с сервисами, которые не знают `card_number` (Сервис подписания, Реестр читателей).

Все изменения `account_id` фиксируются в ReaderHistory.

### Reader

Профиль читателя. Сущность 1:1 с читательским билетом (`card_number`). Содержит `card_number`, `account_id`, признак принятия правил (`rules_accepted`). Абонементы хранятся отдельно в таблице `subscription` (1:N).

Запись создаётся **при первом интеграционном событии**, а не при регистрации на портале. Два пути создания:

1. Пришло Kafka-событие абонемента → создаётся Reader с `rules_accepted=false`, `account_id=null`
2. Пришло RulesSignedEvent → создаётся Reader с `rules_accepted=true`, `account_id` заполнен

_Avoid_: профиль, анкета, пользователь

### RulesSignedEvent

Событие о принятии правил пользования библиотекой, полученное из Сервиса подписания через RMQ. Поля: `document_id`, `document_type`, `account_id`, `status`.

Обрабатывается только при `document_type = LIBRARY_RULES` и `status = signed`. При получении события library-membership:

1. Запрашивает `card_number` в SSO-сервисе по `account_id`
2. Ищет Reader по `card_number`: существует → UPSERT, не существует → создать с `rules_accepted=true`
3. Устанавливает `rules_accepted = true`; `account_id` перезаписывается, если отличается от текущего
4. Идемпотентно — повторные события не меняют состояние
5. Ошибки SSO-сервиса: timeout/5xx → retry → DLQ после исчерпания попыток; 404 → сразу DLQ, без retry

_Avoid_: событие подписания, уведомление о подписи

### Broker

Клиент транспорта (RabbitMQ/Kafka), на котором регистрируются консьюмеры и через который публикуются ответные сообщения.

_Avoid_: транспорт, канал, коннект

### Consumer

Обработчик входящих сообщений, регистрируемый декоратором на брокере.

_Avoid_: Subscriber, подписчик, обработчик очереди

### Message

Объект доставленного сообщения с методами контроля результата обработки: `ack()` — подтвердить, `nack()` — вернуть на повторную доставку, `reject()` — отклонить без повторной доставки (в DLQ).

_Avoid_: Delivery, доставка

### DLQ

Dead-letter очередь, куда уходят сообщения, не обработанные после исчерпания попыток повторной доставки.

_Avoid_: dead-letter, очередь мёртвых сообщений

### Retry queue

Очередь повторной доставки с TTL: возвращает сообщение в основную очередь спустя паузу, пока не исчерпаны попытки (счётчик в заголовке `x-retry-count`); после исчерпания сообщение уходит в DLQ.

_Avoid_: очередь повторов

### Subscription

Абонемент читателя, оформленный через Биллинг. Хранится в таблице `subscription` (1:N к Reader): `external_id` (UUID абонемента из Kafka-сообщения — natural key идемпотентности), `plan_code` (тариф, напр. `basic`, `extended`), `start_date`, `end_date` (`null` — бессрочный).

Активный абонемент = `start_date < now AND (end_date IS NULL OR end_date > now)`. Смена тарифа приходит парой операций: `close` старого абонемента + `create` нового; несколько операций в одном сообщении применяются атомарно.

Идемпотентность — по `external_id`: повторный `create` с тем же содержимым → no-op; `close` уже закрытого → no-op. Изменение `plan_code` у существующего абонемента — фатальная ошибка (`23`).

API отдаёт список активных абонементов читателя (список `plan_code`), а не одно значение тарифа.

_Avoid_: тариф, план, подписка

### Справочник тарифов

Закрытый справочник допустимых `plan_code`. Хранится в БД, наполняется CLI-командой `reference_data seed` (не миграцией). Пришедший `plan_code`, которого нет в справочнике, отклоняется кодом `21`. Справочник расширяется изменением фикстур и повторным запуском команды.

### Биллинг

Внешняя система — источник абонементов. Поставляет их Kafka-событиями; полная сверка реализуется самим Биллингом повторной отправкой текущего состояния в тот же топик.

Если Reader не существует на момент получения абонемента — создаётся с `rules_accepted=false`, `account_id=null`.

_Avoid_: касса, платёжка

### Событие абонемента

Входящее Kafka-сообщение Биллинга. Несёт `correlationId` (корреляция), `cardNumber` и список операций `operations[]`, каждая с `operationType` ∈ {`create`, `close`}, `subscriptionId`, `planCode`, `startDate`/`endDate`.

Структура валидируется по JSON-схеме сообщения. Ответ в reply-топик эхоирует `correlationId` и содержит Код результата.

### Код результата

Целочисленный код обработки события абонемента, возвращаемый в reply:

| Код | Значение |
|---|---|
| `0` | успех (в т.ч. повторный `create`, повторный `close`, уже обработанный `correlationId`) |
| `5` | внутренняя ошибка |
| `21` | неизвестный `planCode` |
| `22` | некорректный диапазон дат (`endDate < startDate`) |
| `23` | `subscriptionId` уже занят абонементом с другим `planCode` (фатально, откат транзакции) |
| `25` | схема сообщения не валидна |

Сопутствующее поле `message` — человекочитаемый текст кода.

При нескольких операциях в одном сообщении побеждает код с наивысшим приоритетом: `5` > `21` > `22` > `23` > `0`. `25` прерывает обработку сразу и в агрегации не участвует.

### Событие изменения абонементов

Исходящее RMQ-уведомление library-membership для портала библиотеки о том, что набор абонементов читателя изменился. Несёт `card_number` и дельту: `added` / `removed` — списки `plan_code`. Публикуется после коммита транзакции, только при непустой дельте. Актуальный список потребитель запрашивает через internal API, а не из события.

### ReaderHistory

Журнал изменений полей Reader. Хранит `changed_data` (JSONB `{"old": {...}, "new": {...}}`) — дифф изменившихся полей (`card_number`, `account_id`, `rules_accepted`); `null` пишется явно. Одна строка на одно реальное изменение; no-op строку не пишет. Только запись, публичного API чтения нет.

Источник изменения — поле `source`: `rules_signed_event`, `billing_event`, `manual_update`.

### ReviewSubmittedEvent

Событие из сервиса отзывов через RMQ: читатель оставил отзыв о книге. Несёт `review_id` и `card_number`. Текст отзыва library-membership добирает из API сервиса отзывов, а не из тела события.

При получении запускается Извлечение предпочтений.

### Извлечение предпочтений

Процесс извлечения структурированных предпочтений читателя из текста отзывов с помощью LLM:

1. Получить текст отзыва
2. LLM сопоставляет текст с существующими `preference_code` (любимые жанры, авторы, формат — бумажная/электронная/аудио)
3. UPSERT в `ReaderPreference` с перезаписью существующих значений
4. Снапшот в `ReaderPreferenceHistory`

Ручного редактирования предпочтений библиотекарем нет — это единственный путь обновления.

_Avoid_: AI-профилирование, автозаполнение

### ReaderPreference

Конкретное значение предпочтения для конкретного читателя. Привязано к Reader по `reader_id`. Тип значения задаётся определением предпочтения (`text`, `number`, `date`, `boolean`, `select`) и определяет, какая колонка `value_*` заполняется.

_Avoid_: интересы, теги

### ReaderSummary

Плоский текст, собираемый на лету из заполненных предпочтений: один буллит `* Название: значение` на предпочтение. Не LLM-генерация, а детерминированная сборка из БД; отдаётся `GET /reader/{reader_id}/summary`. При пустом наборе — пустая строка.

_Avoid_: сводка, выжимка, AI-summary

### ReaderPersonalData

Персональные данные читателя (ФИО, дата рождения, email, телефон), полученные live из внешнего Реестра читателей по `account_id`. Не хранятся в БД library-membership, read-only. Доступны через `GET /reader/{reader_id}/personal_data`.

Недоступность данных — ошибка, а не `null`: читатель не найден → `404`; `account_id` отсутствует или Реестр вернул `404` → `404`; Реестр недоступен (timeout/5xx) → `500`.

_Avoid_: анкета, паспортные данные

### internal API

Внутренний API library-membership для межсервисного взаимодействия (потребитель — портал библиотеки). В отличие от Integration API (Хелпдеск, Мобильное приложение), авторизуется не OAuth2-скоупами, а JWT-токеном сервиса. Поиск читателя — по `account_id` или `card_number`.

_Avoid_: приватный API, backend API

### Контракт выдачи

Свод ограничений на поля ответов integration API (`pattern`, `minLength`/`maxLength`, `minItems`/`maxItems`), собранный в `schemas/integration_api/openapi_types.py`. Каждое сохраняемое значение обязано ему соответствовать, иначе API вернёт ответ, нарушающий собственную OpenAPI-схему. Валидация выполняется на границе записи; нарушение отвергается и ничего не пишется (Kafka — код `5`, RMQ — DLQ, CLI — ошибка).

_Avoid_: схема API, валидация ответа
